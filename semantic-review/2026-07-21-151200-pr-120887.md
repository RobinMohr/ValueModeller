# DB-driven team permissions and Flyway collision resolver

Two unrelated features ship in one PR: the team-permission system moves from hardcoded Python dicts to a database table with admin CRUD endpoints, and a new CI tool resolves Flyway migration version-number collisions automatically. The permissions work is well-structured with a lockout guard, transactional writes, an audit trail, and thorough runbook documentation. The collision resolver is a cleanly layered pipeline utility with integrity verification and race-condition awareness.

Watch for: the two features have zero code overlap and should be separate PRs (confirmed). The `calculate_permissions` call in the authorizer's DB-error except block passes `None` as the cursor, which works only because the team_ids list is empty. There is no validation that the `PUT` request body itself is even JSON (likely handled upstream, but not confirmed). The `SKIP_HISTORY_CHECK: 'true'` default in the pipeline template means the safety net is disabled in practice.

## High-level view

The permissions rewrite replaces `TEAM_PERMISSION_MAPPING` with a `TeamPermissions` DB table and makes `calculate_permissions` take a cursor. The migration seeds the exact previous mapping so the effective permission set per user is identical before and after deploy. A lockout guard prevents removing `admin:manage_roles` from the last team that holds it. An "Ausbilder" virtual team gives trainers DB-driven rights without polluting AzubiTeamMembers.

The Flyway collision resolver is a self-contained CI tool in `ci/flyway_collision_resolver/`. It detects Added-only migrations whose version numbers conflict with the target branch, renumbers them sequentially, verifies SHA-256 integrity, commits, pushes, and comments on the PR. A race-condition re-check fetches the target branch again before pushing.

<summary>Issues (8)</summary>

1. **Two unrelated features in one PR** — split the Flyway collision resolver into its own PR. They share no code and have independent risk profiles.
2. **`SKIP_HISTORY_CHECK` permanently true in pipeline template** — the history safety net (the only guard against renaming already-applied migrations) is disabled for all PR builds. Set it to `false` by default or make it conditional on DB connectivity.
3. **Permission route matching is substring-based** — `"/permissions/" in path` could match unintended future routes (e.g. `/admin/user-permissions/`). Use a prefix check or regex anchored to `/admin/permissions/`.
4. **No input-type validation on PUT body** — if `request_body` is `None` or not a dict (e.g. malformed JSON), the code silently treats it as `{}` and returns a 400 about "permissions must be a list." This is fine functionally but could confuse debugging. An explicit 400 for non-JSON bodies would be clearer.
5. **Authorizer DB-error fallback relies on `calculate_permissions(None, [])` never touching the cursor** — correct today, but one future change to the function could cause an `AttributeError` in production. A defensive `cursor or FakeCursor()` or an explicit short-circuit in the except block is safer.
6. **Collision resolver pushes directly to the PR branch** — if branch policies require reviewers or no direct pushes from bots, this will fail silently (the error handling is good, but the pipeline step doesn't retry).
7. **Role code derived from team name is fragile** — renaming a team (e.g. "Admin" to "Administrators") changes the role code in API responses, potentially breaking frontend guards that match on role strings.
8. **`recruiting:delete_workshops` missing from old `RECRUITING_PERMISSIONS` but present in new `PERMISSION_CATALOG`** — this is intentional (expanding the catalog), but the test `RECRUITING_GRANTS` fixture doesn't include it either, so there's no assertion proving the expansion didn't break resolution for team 2.

## Two unrelated features bundled together

The permissions-in-DB change touches the auth layer, the admin Lambda, shared code, a migration, runbooks, and tests for all of those. The Flyway collision resolver lives entirely under `ci/flyway_collision_resolver/`, `ci/scripts/`, `pipeline_templates/validate.yml`, and its own test files. They share no imports, no runtime code path, and no migration dependency. Reviewing them together makes it harder to assess the security impact of the permissions change in isolation. The collision resolver also modifies `validate_sql_migration_names.sh` (relaxing `{3}` to `{3,}`) which is a prerequisite for its own renumbering, not for permissions. (confirmed)

## Permission resolution: from dict to DB query

`calculate_permissions` now takes a `cursor` as its first argument and executes a `LEFT JOIN` between `AzubiTeams` and `TeamPermissions`. The query uses f-string interpolation for the `IN (...)` placeholders, which is safe here because the values are always `int`-cast `team_ids` from internal lookups, never user input. The query filters resolved grants against `VALID_PERMISSION_KEYS` (a frozenset derived from `PERMISSION_CATALOG`), so stale DB rows for removed keys are silently dropped. This is good defensive design.

The role code is now derived from the team name via regex slugification (`_role_code_from_team_name`). This means renaming a team in the database changes the role code in API responses. If any frontend code or external system matches on role strings (the runbook acknowledges this for "AUSBILDER" vs. the old "ADMIN"), this is a breaking change that happens silently at runtime with no code deploy. (likely)

## Lockout guard and transactional writes

The `PUT /admin/permissions/teams/{teamId}` endpoint validates keys against the catalog, checks whether removing `admin:manage_roles` would leave zero teams with that grant, and then performs a `DELETE` + `INSERT` inside `safe_transaction`. The lockout guard queries `COUNT(DISTINCT TPM_TeamID)` for teams other than the one being edited, which correctly prevents the last-team-with-admin scenario.

One subtlety: the lockout check and the transactional write are not atomic with each other. Between the check and the write, another concurrent request could remove `admin:manage_roles` from the other team. In a low-concurrency admin tool this is acceptable, but worth noting as a TOCTOU window. (possible)

## Ausbilder role-team isolation

The "Ausbilder" team is excluded from user-assignment lists, batch-update, and the ticket dropdown by filtering on `AZT_Name <> 'Ausbilder'`. This is a name-based convention, not a schema-level constraint (no `is_role_team` column or similar). If someone renames the team in the DB, the exclusion breaks and Ausbilder-level permissions could be assigned to trainees. The code references the name via `AUSBILDER_TEAM_NAME` constant, making it easy to find all filter points. (likely)

## Migration safety (V025)

The migration uses `CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`, and a `JOIN` on `AzubiTeams` to avoid FK violations for missing teams. The Ausbilder team creation uses a subquery pattern to work around MySQL error 1093. All statements are idempotent. The test `test_migration_seed_only_references_valid_catalog_keys` reads the migration file from disk and verifies that every seeded key exists in the catalog, which is an effective drift guard.

The runbook and recovery documentation are exceptionally detailed, covering cache propagation timelines, lockout scenarios, and verification queries. This is notably above-average for a migration this size.

## Flyway collision resolver: SKIP_HISTORY_CHECK default

The pipeline template (`validate.yml`) sets `SKIP_HISTORY_CHECK: 'true'`. This means the history safety check (which prevents renaming a migration that was already applied to the database) is disabled for every PR build. The check exists to prevent corrupting `flyway_schema_history`, but it never actually runs. If a developer's migration somehow reaches the DB before merge (e.g. via a staging environment that runs `flyway migrate` on PR branches), the resolver would rename it and cause a checksum mismatch on the next deploy. (confirmed)

## Collision resolver: push and race-condition handling

The resolver re-fetches the target branch after performing renames to detect concurrent merges. If new conflicts are found, it resets the working tree and exits with code 2 (transient, retry). This is a reasonable approach, though the pipeline doesn't actually retry on exit code 2, so the build would just fail and need manual re-trigger.

The `git_push` operation pushes to `origin HEAD:{branch}`. If Azure DevOps branch policies require a PR for any push (even from the build service), or if `persistCredentials` doesn't grant write access, the push fails. The error message is detailed and actionable, which is good.

## Test coverage

The permissions feature has strong test coverage: the resolution logic, the admin routes, the authorizer integration, and a migration-seed integrity test. The collision resolver also has three dedicated test files covering core logic, git integration (with real temp repos), and service mocks.

Not tested: the `routen.py` changes for Ausbilder in the admin handler (the branch where `trainer` is found and permissions are resolved via the new code path has no dedicated test in the diff). The ticket-system `routen.py` change (excluding Ausbilder from the dropdown) has no test. The `main.py` entry point of the collision resolver has no unit test (though the integration tests cover the workflow end-to-end).

## Deleted `auth_utils.py`

The entire `auth_utils.py` (JWT validation, group mapping, permission checking) was deleted. The PR description says it's "unused," but there's no grep or import search visible in the diff confirming nothing else imports it. If another Lambda or test file imported from `admin.auth_utils`, this would break silently. (possible)
